# Database

## DB primario (Supabase, lettura/scrittura)

Contiene i dati della piattaforma. Schema in `supabase/migrations/` (eseguire in ordine).

### Tabelle

**`subscription_plans`** — piani di abbonamento annuali, gestibili dall'admin:
| Colonna | Tipo | Note |
|---|---|---|
| `id` | bigint identity | PK |
| `nome`, `slug` | text | `slug` unico (`[a-z0-9-]`), immutabile dall'interfaccia |
| `descrizione` | text | opzionale |
| `prezzo_annuale` | numeric(10,2) | ≥ 0 |
| `tipo_prezzo` | text | `importo`/`gratis`/`su_richiesta` (default `importo`, migration 0010): come mostrare il prezzo; con `su_richiesta` il piano **non è attivabile self-serve** (guard del backend su cambio piano e registrazione, resta assegnabile dall'admin) |
| `etichetta_prezzo` | text | mostrata al posto del prezzo SOLO con `su_richiesta`; NULL/vuota ⇒ la UI mostra «Su richiesta» (nessun check cross-campo) |
| `ai_check` | integer | numero di AI-check inclusi/anno |
| `alert_attivo` | boolean | se true, `alert_giorni_preavviso` è obbligatorio (check `plans_alert_coherence`) |
| `alert_giorni_preavviso` | integer | > 0 o NULL (preavviso scadenze — funzione futura) |
| `alert_ritardo_giorni` | integer | ≥ 0 o NULL (migration 0021): ritardo dell'alert nuovi-bandi dalla pubblicazione; NULL = feature esclusa dal piano |
| `num_account_aziendali` | integer | ≥ 1 |
| `features_override` | text[] | NULL (migration 0029): bullet custom della card piano; NULL = testo derivato dai campi numerici (template PlanCard). Usato dal piano `tailored` |
| `partner_calls_attive_max`, `partner_candidature_mese` | integer | default 0, ≥ 0 o NULL (migration 0036): call di partenariato attive e candidature al mese, sul pool del titolare; **NULL = illimitato, 0 = esclusa** (semantica opposta ad `alert_ritardo_giorni`) |
| `partner_bozze_mese` | integer | default 0, ≥ 0 o NULL (migration 0042): bozze AI dei documenti del partenariato (lettera d'intenti, NDA, term sheet) per mese solare Europe/Rome, sul pool del titolare; **NULL = illimitato, 0 = esclusa** |
| `ordering`, `is_active` | int, bool | ordinamento in UI; i piani non si eliminano, si disattivano |

**`profiles`** — 1:1 con `auth.users` (PK = `auth.users.id`, on delete cascade): `email` (denormalizzata per la ricerca admin), `nome`, `cognome`, `azienda`, `telefono` (in **E.164** per i valori scritti dalla 0022 in poi; i precedenti restano testo libero finché non modificati), `job_position_id`/`job_position_altro` (posizione aziendale, migration 0022 — vedi sotto), `role` (enum `admin`/`cliente`/`progettista` — il terzo valore arriva dalla migration 0014, in un file a sé perché un valore enum non è usabile nella stessa transazione che lo crea), `is_active` (bool, default true).

**`user_subscriptions`** — storico abbonamenti: `user_id` → profiles, `plan_id` → plans, `status` (enum `active`/`cancelled`/`expired`), `data_inizio`, `data_scadenza` (default +1 anno). Indice unico parziale `user_subscriptions_one_active` ⇒ **un solo abbonamento `active` per utente**; il cambio piano cancella l'attivo e ne crea uno nuovo (lo storico resta).

### Famiglie di account (migration 0003)

**`family_members`** — membership e inviti in un'unica tabella (una riga per "permanenza"): `parent_id`/`member_id` → profiles (FK con nomi espliciti per gli embed PostgREST), `denominazione`, `invited_email`, `invite_kind` (`new_user`/`existing_user`), `status` (`pending` → `active` → `demoted`; terminali: `removed`, `declined`), `invited_at`, `joined_at` (chiave d'ordine per le retrocessioni), `demoted_at`, `removed_at`. **Indice unico parziale**: un utente può avere una sola membership corrente (pending/active/demoted). Regole: il limite account del piano **include il padre**; i figli attivi **non hanno un abbonamento proprio** (ereditano dal padre); le quote sono condivise a livello famiglia.

**`company_profiles`** — dati aziendali, uno per padre: ragione sociale, P.IVA (check 11 cifre), forma giuridica, ATECO/settore/regione (id delle lookup del DB secondario + copie testo denormalizzate, nessuna FK cross-DB), **`beneficiari` jsonb** `[{id, nome}]` (categorie **dichiarate** dall'utente dalla stessa lookup del catalogo, multi-valore, check `jsonb_typeof = 'array'`: non si deducono dalla visura — vedi 0011), sede legale (CAP check 5 cifre), classe dimensionale, dipendenti, fascia fatturato, PEC/telefono/sito.

**`audit_log`** — operazioni sensibili (inviti, retrocessioni, rimozioni, cambi piano, modifiche dati aziendali), senza FK: le righe sopravvivono alla cancellazione degli utenti. Consultabile dal SQL Editor.

**`auth_tokens`** (migration 0004) — token monouso per i link email di dominio (conferma indirizzo, recovery, inviti): `user_id` → profiles (cascade), `purpose`, `token_hash` (SHA-256, unico — il token in chiaro non viene mai salvato), `expires_at`, `used_at`. Consumo atomico via UPDATE condizionato.

### Dati certificati, preferenze e consumi (migration 0005)

**`profiles`** (colonne aggiunte) — `codice_fiscale` (16 caratteri maiuscoli, check di formato) e `cf_verified_at` (verifica all'Anagrafe Tributaria via openapi.it). Il trigger `fn_reset_cf_verification` azzera la verifica se il CF cambia, tranne quando lo statement imposta esplicitamente anche `cf_verified_at` (flusso di verifica).

**`company_data`** — la "visura" certificata da openapi.it (endpoint IT-full), **una riga per azienda** (`company_profile_id` unico → company_profiles, cascade): `raw` jsonb è il payload completo (fonte di verità), `derived` jsonb i valori calcolati all'import (divisione ATECO, ATECO secondari, match regione, `regioni_ids` di tutte le sedi, classe dimensionale, fasce — **non** i beneficiari, che sono dichiarati su `company_profiles`), più estratti "caldi" (`denominazione`, `stato_impresa`), `piva_fetched` (check 11 cifre), `sandbox`, `fetch_count`, `fetched_at`. Solo l'ultima versione: lo storico dei recuperi vive in `audit_log` + `api_usage_events`.

**`company_people`** — persone estratte dalla visura a ogni import (replace-all): `kind` (`manager`/`shareholder`/`auditor`), anagrafica, `ruoli` jsonb, `is_legale_rappresentante`, `quota_percentuale`, frammento `raw` originale. Cascade da company_profiles.

**`user_preferences`** — preferenze di filtro/notifica **per utente** (anche i figli hanno le proprie): una riga per (utente, faccetta, id lookup del secondario) con `facet` vincolata alle 7 faccette dei bandi, `label` denormalizzata (nessuna FK cross-DB), unique su (user_id, facet, ref_id). Cascade da profiles.

**`api_usage_events`** — registro dei consumi API a pagamento, **senza FK** (come audit_log: sopravvive alle cancellazioni): provider/service/outcome (`success`/`error`/`timeout_unknown`), `cost_cents`, `response_status`, `request_meta` (mai dati personali in chiaro). Per l'AI-check annota ogni esito con `provider='anthropic'`, `service='ai_check'` e i token consumati nel `request_meta` — ma è un registro di SPESA best-effort: il **conteggio quota** usa le righe di `ai_checks` (`pending`+`ready` nella finestra dell'abbonamento), che cambiano stato atomicamente e sono transazionali col risultato.

**`company_import_locks`** + `fn_acquire_import_lock(parent_id, ttl)` / `fn_release_import_lock(parent_id)` — lock anti doppia-spesa per l'import: la chiamata HTTP esterna avviene tra statement PostgREST, quindi il claim è un INSERT atomico con "furto" solo se il lock esistente è scaduto (TTL clampato a 600s). Riusato anche dalla verifica CF.

**`company_import_drafts`** (migration 0013) — payload IT-full **già pagato**, in attesa che l'utente confermi l'anteprima: una riga per titolare (`parent_id` PK → profiles, cascade), `partita_iva` (check 11 cifre), `raw` jsonb, `sandbox`, `fetched_at`, `expires_at` (indicizzato). Esiste perché la chiamata costa: rifarla alla conferma raddoppierebbe la spesa, e una cache in memoria non sopravvive al multi-worker. **Non è un dato aziendale** — nessuna pagina lo legge, non entra nell'AI-check né nel punteggio di compatibilità — quindi il vincolo «nulla è salvato finché non confermi» resta rispettato. Le letture filtrano sempre su `expires_at > now()`: la scadenza è un filtro, non una cancellazione (non c'è job di pulizia; un nuovo recupero sostituisce la riga con un upsert). Chi annulla non lo perde: entro il TTL l'anteprima si ricostruisce gratis. RLS deny-all + revoke, come i lock.

### AI-check (migration 0007)

**`bando_requirements`** — cache delle estrazioni LLM per bando (indipendente dall'azienda, una riga per `bando_id` — id intero del DB secondario, **senza FK cross-database**): `content_hash` (hash_bando del catalogo, fallback sha256 dell'input serializzato), `prompt_version`, `model`, **`extraction` jsonb** (requisiti obbligatori + criteri di valutazione + griglia, con citazioni), token consumati. Aggiornata in place quando cambia hash o versione dei prompt: l'estrazione si paga una volta sola per bando, tutte le aziende la riusano.

**`ai_checks`** — report di compatibilità azienda↔bando (**storico versionato**: ogni generazione è una nuova riga, la più recente è in evidenza): `company_profile_id` (cascade), `user_id` (richiedente, senza FK), `family_parent_id` (chiave di visibilità e quota), `bando_id`/`bando_slug`/`bando_titolo` denormalizzati (lo storico sopravvive al bando), `status` (`pending`→`ready`/`error`), **`esito`** (`ammissibile`/`non_ammissibile`/`da_verificare`), **`punteggio`** (0-100) e **`tipo_punteggio`** (`stima`/`euristico`) come colonne per le liste, **`report` jsonb** completo (requisiti con verdetti e citazioni, criteri, verifiche strutturate, punti di forza/debolezza, dati mancanti), `model`, `prompt_version`, `extraction_cached`, token e `cost_cents` reali. Indice unico parziale: al massimo UNA analisi `pending` per coppia azienda×bando.

### Bandi salvati e calendario (migration 0008)

**`saved_bandi`** — preferiti per utente: riferimento al catalogo del secondario **senza FK cross-database** (`bando_id` intero) con snapshot denormalizzati (`bando_slug`, `bando_titolo`, `data_scadenza`, `stato_bando`) che sopravvivono alla scomparsa del bando e fanno da fallback di visualizzazione. `unique (user_id, bando_id)`; cascade da profiles; righe immutabili (niente updated_at).

**`calendar_events`** — eventi del calendario personale: `titolo` (1-200), **`data` `date` + `ora_inizio`/`ora_fine` `time` senza fuso** (calendario italiano wall-clock, come `data_scadenza` del catalogo), `tutto_il_giorno`, `note` (≤2000), `tipo` (`personale`/`bando`). CHECK di coerenza: `tipo='bando'` ⇔ `bando_id`+`bando_slug` presenti; tutto il giorno ⇒ niente orari, con orari ⇒ inizio obbligatorio e fine successiva. Indice unico parziale `(user_id, bando_id) where tipo='bando'`: **una sola scadenza in calendario per bando per utente** (idempotenza). Nessuna FK verso saved_bandi: preferiti ed eventi sono indipendenti.

### Add-on (migration 0009)

**`addons`** — catalogo add-on acquistabili gestito dagli admin, gemello di `subscription_plans`: `nome`, **`slug` unico** (identificativo STABILE per agganciare le funzionalità future), `descrizione`, `prezzo numeric(10,2) ≥ 0` (euro, stessa convenzione dei piani), `tipo_prezzo`/`etichetta_prezzo` (migration 0010, stessa semantica dei piani), **`tipo_fruizione`** (migration 0028: `consumabile`/`permanente`), **`risorsa`** (migration 0030: `seats`/`companies`/NULL — l'aggancio al motore entitlement, vedi sezione dedicata), `ordering`, `is_active`. Come i piani, **non si eliminano: si disattivano**. Il catalogo parte vuoto, con un'eccezione: la migration 0017 garantisce con un seed idempotente l'addon **`consulto-esperto`** (aggancio del flusso consulenze; slug in `consulting_addon_slug` del backend). Dal modulo pagamenti gli add-on **a pagamento** si comprano dal checkout (`POST /me/checkout` con `addon_slug`): l'acquisto pagato accredita un'**unità** nell'inventario add-on (**migration 0028**: `user_addon_inventory` + `addon_ledger`; fino alla 0028 era un credito riga-per-riga in `user_addons`) che la funzionalità agganciata consuma — per `consulto-esperto` la consuma `fn_create_consultation_request` alla creazione della richiesta (senza unità: `409 payment_required`); con l'addon `gratis` (seed attuale) il flusso resta senza pagamento.

### Modalità di visualizzazione prezzo (migration 0010)

Su `subscription_plans` e `addons`: `tipo_prezzo text not null default 'importo'` con check sui tre valori (`importo`, `gratis`, `su_richiesta` — valori di dominio in italiano come `tipo_punteggio`/`esito`) ed `etichetta_prezzo text` libera. La migration fa un **backfill una tantum**: tutto ciò che aveva prezzo 0 diventa `gratis` (nel seed è il piano Gratuito); i record creati a 0 € in seguito restano `importo` finché l'admin non li cambia. Il valore numerico del prezzo resta sempre salvato, anche quando non è mostrato.

### Progettisti (migration 0014–0015)

**`progettisti`** — attributi del ruolo progettista, 1:1 con profiles (PK `user_id`, cascade): **`codice`** leggibile `PRG-00001` (sequence, unico, **immutabile** — un trigger `BEFORE UPDATE` rifiuta il cambio con detail `codice_immutabile`), `bio`, `specializzazioni` (descrittiva, predisposta per un futuro routing per specializzazione, oggi non filtrata). La riga **sopravvive alla demozione**: una ri-promozione riusa lo stesso codice, così i riferimenti storici restano coerenti.

`fn_promote_progettista(p_user_id, p_actor_id) → codice` — promozione atomica (lock `FOR UPDATE` sul profilo): imposta `role='progettista'`, assegna il codice solo se assente e registra `admin.progettista_promoted` in audit_log. Chiamata da `admin_update_user`; la demozione è un update di ruolo normale (anch'esso in audit_log come `admin.role_changed`).

### Notifiche in-app (migration 0016)

**`notifications`** — il canale AFFIDABILE degli eventi applicativi (le email sono best-effort): `user_id` → profiles (cascade), `tipo` (codice macchina, es. `consulenza.nuova_richiesta`), `titolo` (1-200), `corpo` (≤1000), `url` (deep-link in-app), **`dedup_key` NOT NULL** con **constraint pieno** `unique (user_id, dedup_key)` — è l'arbiter dell'upsert ignore-duplicates di PostgREST (un indice parziale non lo sarebbe): il retry di un fan-out inserisce solo i destinatari mancanti. `read_at` per il badge (indice parziale sulle non lette). **Minimizzazione**: titolo/corpo non contengono dati personali di terzi; i dettagli si leggono seguendo `url`, dove l'endpoint applica l'autorizzazione live — una notifica recapitata a un progettista non trattiene dati di un cliente che poi si cancella.

### Consulenze (migration 0017)

Flusso: richiesta (`nuova`) → proposte dei progettisti → accettazione = **assegnazione definitiva 1:1** (+ prenotazione slot opzionale). Stati con `text + check` (pattern ai_checks). Chi riferisce persone segue il pattern di `ai_checks`: `cliente_id`, `family_parent_id`, i `progettista_id` di proposte/booking **senza FK** (lo storico sopravvive alle persone); `company_profile_id` con cascade (lo storico muore con l'azienda: right to erasure del titolare).

**`availability_slots`** — disponibilità del progettista in **UTC** (`timestamptz` — divergenza deliberata dal wall-clock di `calendar_events`: qui due utenti diversi guardano lo stesso istante, la UI mostra il fuso del browser). Anti-sovrapposizione a livello DB: `exclude using gist (progettista_id with =, tstzrange(inizio, fine) with &&)` (estensione `btree_gist`; range `[)`: slot adiacenti validi). Nessuna colonna di stato: «libero» = nessun booking confermato. Dalla **0018**: `serie_id uuid` nullable (indice parziale `where serie_id is not null`) — raggruppa gli slot nati da una ricorrenza, nessuna tabella madre; modificare una singola occorrenza non la stacca dalla serie.

**`consultation_requests`** — la richiesta di consulto: snapshot dell'AI-check (`ai_check_id` set null + `esito`/`punteggio`), bando denormalizzato, `addon_id`/`addon_slug`/`addon_prezzo` (innesto del futuro pagamento), `stato` (`nuova`/`assegnata`/`annullata`, con check di coerenza: assegnata ⇔ progettista+proposta+data valorizzati). Indice unico parziale `(family_parent_id, bando_id) where stato='nuova'`: **una sola richiesta aperta per bando per azienda** — una richiesta già assegnata non blocca un futuro secondo consulto sullo stesso bando. Dalla **0041** l'indice vale per i consulti da AI-check (`partner_call_id` NULL) e un secondo indice tiene un consulto aperto per call di partenariato: i due consulti coesistono sullo stesso bando (vedi la sezione 0041).

**`consultation_proposals`** — proposte dei progettisti: `stato` (`inviata`/`accettata`/`rifiutata`/`superata`/`ritirata`). Indice unico parziale `(request_id, progettista_id) where stato='inviata'`: una sola proposta **aperta** per progettista; dopo un ritiro o un rifiuto se ne può inviare una nuova.

**`consultation_bookings`** — appuntamenti: `slot_id` → availability_slots **on delete set null** + snapshot `inizio`/`fine` (l'appuntamento sopravvive allo slot e alla cancellazione dell'account del progettista). Indici unici parziali `(slot_id) where stato='confermata'` (anti doppia prenotazione a livello DB) e `(request_id) where stato='confermata'` (un appuntamento attivo per consulenza). L'annullamento libera lo slot da solo. Dalla **0020**: `videocall_token uuid` (default `gen_random_uuid()`, unique) — la stanza Jitsi dell'appuntamento.

RPC (SECURITY DEFINER, errori a detail-code, ordine di lock uniforme richiesta→slot):
- `fn_accept_proposal(request, proposal, cliente, slot?)` — `FOR UPDATE` su richiesta **e proposta** (un ritiro concorrente non può essere sovrascritto: l'accettazione si mette in coda dietro il suo lock); guardie su titolare, stato, e autore ancora attivo con ruolo progettista **o admin** (`progettista_not_available`; parità admin, 0019); chiude le altre proposte come `superate`; con `slot` prenota nella stessa transazione (**all-or-nothing**: slot preso ⇒ salta anche l'assegnazione, detail `slot_taken`). Audit `consulenza.assigned` (+ `consulenza.booked`).
- `fn_book_slot(request, slot, actor)` — serializza sullo slot (`FOR UPDATE`); l'indice parziale resta il backstop e il suo 23505 viene ricatturato come `slot_taken` (senza, il client vedrebbe 502 invece di 409).
- `fn_update_slot` / `fn_delete_slot` — anche il CRUD dello slot serializza sulla riga: un update condizionale non basterebbe (in READ COMMITTED la subquery userebbe lo snapshot preso prima del lock e non vedrebbe una prenotazione appena committata). Slot prenotato ⇒ `slot_booked`.

### Serie di slot ricorrenti (migration 0018)

Le **occorrenze** di una ricorrenza («ogni giorno / giorno feriale / settimana / mese») le materializza il **browser**, non il DB: solo il client conosce il fuso dell'utente, e l'orario a muro deve restare stabile attraverso i cambi di ora legale. Il backend valida ogni occorrenza come uno slot singolo e passa dalle RPC:
- `fn_create_slot_serie(progettista, occorrenze jsonb) → jsonb` — transazione unica con blocco `begin/exception` per riga: le occorrenze che violano l'exclusion constraint vengono **saltate** (anche quelle sovrapposte tra loro nel payload), non abortiscono la serie — un bulk insert PostgREST sarebbe all-or-nothing. Guardie: `serie_vuota`, `serie_troppo_lunga` (>370, allineato a `MAX_OCCORRENZE_SERIE` del backend), `serie_tutta_sovrapposta` se nessuna entra (409). Ritorna `{serie_id, creati, saltati}`.
- `fn_delete_slot_serie(serie, progettista) → jsonb` — `FOR UPDATE` sulle righe della serie prima del delete (stessa ragione di `fn_update_slot`: il `not exists` sul booking va rivalutato dopo il lock), poi cancella i soli slot **senza** prenotazione confermata. Ownership = coppia `(serie_id, progettista_id)`, altrimenti `serie_not_found`. Ritorna `{eliminati, mantenuti}`.

### Parità admin (migration 0019)

Decisione di prodotto: gli **admin hanno le stesse funzioni dei progettisti** (pool, proposte, slot, appuntamenti), senza cambiare ruolo. A DB:
- `fn_ensure_progettista_codice(user) → text` — codice PRG **pigro**: il backend la chiama alla prima proposta di un admin. `FOR UPDATE` sul profilo (serializza prime-proposte concorrenti; `user_not_found` se assente), poi «insert solo se assente» in `progettisti` con la stessa sequence di `fn_promote_progettista` — le due funzioni condividono la riga: una promozione riusa il codice pigro e viceversa. Nessun cambio di ruolo, nessun audit di promozione.
- `fn_accept_proposal` **ridefinita** (corpo integrale della 0017 con una riga cambiata): la guardia sull'autore della proposta accetta `role in ('progettista','admin')` attivo — con la 0017 una proposta di un admin non sarebbe mai stata accettabile. CREATE OR REPLACE conserva le revoche.

### Videochiamate (migration 0020)

Ogni appuntamento nasce con la sua stanza Jitsi: colonna `videocall_token uuid not null default gen_random_uuid()` **unique** su `consultation_bookings`. L'istanza Jitsi self-hosted è **aperta** (niente JWT): la sicurezza sta nel nome-stanza non indovinabile, quindi il token è un **segreto** — generato una sola volta all'INSERT (gli update non lo toccano mai: idempotenza per costruzione), mai esposto nelle notifiche conservate. A DB vive solo il token; l'**URL** (`{JITSI_BASE_URL}/bandofit-{token}`) lo deriva il backend, così un cambio di istanza non richiede backfill. Ri-prenotazione = riga nuova = token nuovo; l'annullo lo nasconde da solo (le letture filtrano `stato='confermata'`). Retroattività: l'`ADD COLUMN` con default **volatile** riscrive la tabella valutando il default per riga → anche le prenotazioni pre-esistenti hanno ricevuto un token proprio e distinto.

### Alert nuovi bandi (migration 0021)

**Nessuna pre-schedulazione**: il job giornaliero (scheduler in-process, claim per insert su `bando_alert_runs` — PK `giorno`, un 23505 = già eseguita) ricalcola l'idoneità a OGNI run dallo stato corrente; gli edge case su cambio piano, ritiro del bando e opt-out tardivo si risolvono da soli. Oggetti:
- `subscription_plans.alert_ritardo_giorni` — giorni di ritardo dalla pubblicazione (0 = stesso giorno; NULL = feature esclusa dal piano). Semantica DIVERSA da `alert_giorni_preavviso` (promemoria scadenze, funzione futura, intatto).
- **`bando_alert_settings`** — opt-in/out per utente (riga pigra: assenza = abilitati) + `unsubscribe_token` unico: il link RFC 8058 nelle email e il toggle in Preferenze scrivono la STESSA riga.
- **`bando_alert_sends`** — ledger idempotenza, `unique (user_id, bando_id)` come arbiter del claim-by-insert. Stati: `in_invio → inviata | fallita` (ritentabile fino a 3 tentativi) ; `incerta` = run interrotta tra invio e conferma, MAI ritentata (at-most-once). Nessun contenuto personale (minimizzazione).
- **`bando_alert_runs`** — una riga per esecuzione con i contatori (candidati/destinatari/inviate/fallite): l'osservabilità del job.

### Inventario add-on a quantità + ledger (migration 0028)

Sostituisce il modello riga-per-credito di `user_addons` (0026) con un **inventario a quantità** e un **registro append-only**: il saldo è sempre ricostruibile dai movimenti (`quantita = sum(delta)`). Da eseguire **in un'unica transazione**, idempotente dove indicato, con rollback documentato in coda al file. `user_addons` **non viene droppata**: resta **congelata** (sola lettura storica) come rete di rollback, non più scritta. Decisioni di prodotto (2026-07-20): gating consulto attivo da subito (la riga di catalogo è già a pagamento in produzione); **nessun rimborso automatico** (il tipo `refund` è predisposto ma non emesso — una restituzione la fa l'admin col grant); addon **permanenti** solo predisposti.

**`addons.tipo_fruizione`** (`consumabile`/`permanente`, default `consumabile`, `check`) — come si fruisce un addon: `consumabile` = unità a quantità (si compra N volte, si consuma); `permanente` = possesso binario (0 o 1). **Immutabile dopo la creazione**, come lo slug (cambiarlo con inventario circolante ha semantica indefinita). L'addon `consulto-esperto` è `consumabile`; il gating si accende **da sé** quando la riga è `consumabile AND tipo_prezzo='importo' AND prezzo>0` — prezzo e tipo li gestisce l'admin da AdminAddon, non la migration.

**`user_addon_inventory`** — saldo **materializzato** per `(utente, addon)` (PK composita): `quantita integer ≥ 0` (il `check` è l'**arbitro del consumo**: un decremento sotto zero è «esaurito»), `updated_at` (trigger). **Cache del ledger**: scritta SOLO via `fn_addon_apply_movement`, mai a mano. `user_id` → profiles **cascade** (l'inventario muore con l'utente); per i permanenti `quantita ∈ {0,1}` (fatto rispettare da RPC/checkout). RLS deny-all + `REVOKE ALL` ai ruoli client.

**`addon_ledger`** — registro **APPEND-ONLY** dei movimenti (`id` identity; `user_id` **senza FK** — come `purchases`/`api_usage_events`: il registro sopravvive alla cancellazione dell'utente, mentre l'inventario cade in cascade): `tipo` (`purchase`/`admin_grant`/`consume`/`refund`/`admin_revoke`), `delta` intero, `purchase_id` → purchases, `request_id` (id della richiesta di consulto, **senza FK**: muore col cascade dell'azienda), `actor_id`, `note`, `created_at`. Due `check` di coerenza: sul **segno** del delta per tipo (`purchase`/`admin_grant` > 0, `consume` = −1, `refund` = +1, `admin_revoke` < 0) e sui **riferimenti obbligatori** per tipo (un accredito cita il purchase; un grant/revoca citano attore e nota; consumo/rimborso citano la richiesta). **Append-only anche per il `service_role`** (che bypassa la RLS): il trigger `addon_ledger_readonly` (`fn_addon_ledger_readonly`) rifiuta ogni UPDATE/DELETE. **Idempotenza a DB** con indici parziali UNIQUE: un `consume` e un `refund` al più per richiesta, una entry di accredito (`purchase`/`admin_grant`) al più per purchase — il delta può però essere +N. Indice `(user_id, addon_id, created_at desc)` per lo storico a scomparsa. RLS deny-all + `REVOKE ALL` ai ruoli client.

**`purchases.kind += 'addon_admin'`** — grant addon gratuito da admin: una riga a **0 €** nello storico, gemella di `cambio_admin` (esclusa dai ricavi per costruzione). Il vincolo `purchases_cambio_admin_coerente` diventa **`purchases_gratuito_admin_coerente`** e lo **generalizza**: i kind `cambio_admin` **e** `addon_admin` sono `status='gratuito'` con `actor_admin_id`, `motivazione` e `totale_cents=0` (e `addon_id` valorizzato per `addon_admin`); ogni altro kind non è mai `gratuito`. Il `kind_check` accetta ora `piano`/`rinnovo`/`addon`/`cambio_admin`/`addon_admin`.

RPC (SECURITY DEFINER, EXECUTE revocato ai ruoli client):
- **`fn_addon_apply_movement(user, addon, tipo, delta, purchase_id, request_id, actor_id, note) → quantità residua`** — **unico punto di scrittura** (ledger + inventario), sempre chiamata dentro la transazione di un'altra RPC; il saldo non va mai negativo. Accredito e decremento sono percorsi diversi: l'accredito è `INSERT … ON CONFLICT DO UPDATE`, il decremento è un `UPDATE` con row-lock il cui `check(quantita ≥ 0)` (o l'assenza di riga) diventa `addon_credit_esaurito` — in `ON CONFLICT` il check verrebbe valutato sui VALUES proposti prima di risolvere il conflitto, quindi un −1 fallirebbe comunque.
- **`fn_create_consultation_request(payload jsonb) → jsonb`** — insert della richiesta di consulto **e consumo di 1 unità ATOMICI** (se il saldo è 0 l'eccezione annulla anche l'insert). Il **gating lo RICALCOLA la RPC** leggendo il catalogo nella stessa transazione (niente TOCTOU col pre-check Python): `consumabile AND importo AND prezzo>0` ⇒ serve 1 unità. Traduce in detail-code il 23505 dell'indice `consultation_requests_one_open` (`request_gia_aperta`), l'addon assente (`addon_not_available`) e il saldo esaurito (`addon_credit_esaurito`). Idempotente per costruzione (richiesta appena creata) + UNIQUE `consume` per richiesta. Ritorna `{request, consumato, quantita_residua}`.
- **`fn_complete_purchase` riscritta** — corpo verbatim della 0026 salvo due punti: (a) i kind amministrativi (`cambio_admin`/`addon_admin`, gratuiti) **non si completano con un pagamento** (`invalid_kind`); (b) il ramo `addon` ora **accredita nel ledger** (`fn_addon_apply_movement`, tipo `purchase`, +1), **non più in `user_addons`** — un addon **permanente** già posseduto non si duplica e torna `pagamento_orfano` `addon_gia_posseduto` (il denaro è registrato, il rimborso è manuale in v1). Un purchase addon = 1 unità in v1; il ledger supporta già +N (estensione futura del checkout).
- **`fn_admin_grant_addon(admin, user, addon, quantita, motivazione) → jsonb`** (R5) — accredito gratuito da admin: **motivazione obbligatoria** (`motivation_required`), **quantità ≥ 1** (`quantita_non_valida`), utente e addon esistenti (`user_not_found`/`addon_not_available`); per i **permanenti** quantità = 1 e non già posseduto (`addon_gia_posseduto`). Crea la riga `purchases` `addon_admin`/`gratuito` a 0 € (NON annulla il checkout in corso dell'utente) e applica il movimento `admin_grant` (+quantità). Audit `addon.granted`. Ritorna `{purchase_id, quantita_residua}`.
- **`fn_admin_revoke_addon(admin, user, addon, quantita, motivazione) → jsonb`** (R5) — revoca unità (`FOR UPDATE` sulla riga, serializza con consumi/grant concorrenti): **clampata al residuo** (`least`; non si revocano unità già consumate; `niente_da_revocare` se saldo 0), motivazione obbligatoria. Audit `addon.revoked`. Ritorna `{quantita_revocata, quantita_residua}`.
- **`fn_backfill_addon_ledger_0028() → jsonb`** — backfill **idempotente** dallo storico: ogni `user_addons` diventa una entry `purchase` (+1, `created_at` originale) e, se consumata con ref valido, una `consume` (−1); i purchase addon pagati senza credito recuperano l'unità; le righe consumate con ref NULL/malformato si saltano **in coppia** (saldo netto 0) e si tracciano in audit (`addon.backfill_skipped`). L'**inventario si RICOSTRUISCE dal ledger** (l'invariante di R3). Chiamata alla fine della migration; un blocco di verifica **ABORTISCE** la migration se il saldo diverge dal ledger o è negativo.

**Invariante `saldo = ledger`**: `user_addon_inventory.quantita` è per costruzione `sum(addon_ledger.delta)` per ogni `(utente, addon)` — la migration lo verifica in coda e abortisce se rotto.

### Motore entitlement (migration 0030)

Un'unica formula per i limiti quantitativi: **`effettivo = base (piano) + extra (unità di addon allocativi possedute)`**, per tre risorse — `seats` (account della famiglia, `num_account_aziendali`, include il titolare), `companies` (aziende gestibili, `coalesce(max_aziende_override, max_aziende, 1)`), `ai_checks` (AI-check per ciclo, `ai_check`). **Dormienza**: se la base non abilita la capability (=1, o =0 per ai_checks) l'extra NON si somma — la capability è del piano, l'addon estende la capacità; le unità restano possedute e tornano attive con un piano idoneo (così i predicati booleani «multi» sparsi — `is_multi` del resolver, gate alert — restano equivalenti). Migration additiva e behavior-preserving: senza addon allocativi ogni numero è identico a prima.

- **`addons.risorsa`** (`seats`/`companies`, NULL = addon normale) — la mappatura addon→risorsa su cui chiavizza il motore (**mai sullo slug**, che resta stabile per deep-link e snapshot storici). v1 senza `ai_checks` (un boost permanente per-ciclo va progettato a parte). CHECK `addons_risorsa_consumabile`: un allocativo non può essere `permanente`. Immutabile dopo la creazione, come slug e tipo_fruizione.
- **`purchases.quantita`** (default 1, CHECK 1..100) — unità acquistate/accreditate con la riga; gli importi della riga restano TOTALI. Backfill in-migration dei grant admin esistenti da `dettaglio_calcolo->>'quantita'`.
- **`fn_entitlement_detail(user, risorsa) → (base, extra, effettivo)`** — LA formula (unica sede della dormienza); `fn_entitlement_limit` ne espone l'effettivo, `fn_entitlement_extra` somma l'inventario allocativo (senza filtro `is_active`: disattivare un addon ferma le vendite, non spoglia chi ha comprato).
- **`fn_entitlement_snapshot(user) → jsonb`** — fotografia read-only per il backend (`GET /me/entitlements` e i serializer esistenti): per ogni risorsa base/extra/effettivo/usato/residuo (+`periodo_inizio`/`periodo_fine` per ai_checks, stessa semantica di conteggio di `get_quota`: righe `ai_checks` pending|ready nella finestra del ciclo).
- **`fn_family_limit` / `fn_effective_max_aziende` → WRAPPER** di `fn_entitlement_limit`: tutti gli arbitri esistenti (`fn_create_family_member`, `fn_accept_invitation`, `fn_reactivate_family_member`, `fn_create_company`, `fn_reconcile_companies`) applicano l'effettivo senza essere toccati. Lato Python `family_service.family_limit` legge il wrapper via RPC (non più la colonna) e la quota AI-check esce dallo snapshot: display e arbitri non possono divergere.
- **`fn_reconcile_family(owner, actor, reason) → jsonb`** — il loop di adeguamento famiglia estratto da `fn_apply_plan_change` (revoca inviti pending più recenti → retrocede attivi più recenti, limite EFFETTIVO), riusato dalla revoca admin di addon seats. `fn_apply_plan_change` è riscritta per usarlo (validazione `plan_not_available` invariata; il limite si risolve DOPO l'insert della nuova subscription, così gli addon seats contano).
- **`fn_complete_purchase`** — il ramo addon accredita **`purchases.quantita`** unità (entry unica di ledger con delta +N; un permanente esige quantita=1, altrimenti `pagamento_orfano` con motivo `quantita_non_valida`).
- **`fn_admin_grant_addon`** — persiste la quantità in colonna; nuova guardia `addon_risorsa_solo_titolare`: un addon allocativo NON si accredita a un membro di famiglia ATTIVO (l'extra si somma sull'inventario dell'owner: le unità del figlio resterebbero dormienti e invisibili).
- **`fn_admin_revoke_addon`** — locka il **profilo PRIMA** della riga inventario (ordine lock globale profilo→inventario) e, dopo la revoca di un allocativo, **riconcilia SUBITO** (decisione B3): seats → `fn_reconcile_family` (reason `addon_revoked`), companies → `fn_reconcile_companies`.
- **`fn_canonizza_addon_0030()`** — canonizzazione richiamabile (pattern backfill 0028, testabile sul harness a DB vuoto) dei due addon allocativi creati in produzione da console: `profilo-aziendale-aggiuntivo` → risorsa `seats`, nome «Account collegato aggiuntivo»; `azienda-aggiuntiva` → risorsa `companies`, nome «Azienda aggiuntiva» (+descrizioni nuove, `tipo_fruizione='consumabile'` a difesa del CHECK). ### Appartenenza, visibilità e budget dei membri (migration 0031)

Due concetti distinti per i membri della famiglia: **appartenenza** (`family_members.company_profile_id`, UNA azienda di riferimento, scelta dal titolare all'invito — la RPC la esige se l'owner ha più aziende vive, la assegna da sola se ne ha una, la lascia NULL senza aziende) e **visibilità** (`family_member_company_access`, PK membership×azienda: l'insieme concesso, con INVARIANTE **visibilità ⊇ appartenenza** — RPC di scrittura + trigger `access_protegge_appartenenza` che vieta il DELETE della riga di appartenenza, tranne in cascata). Le righe access sopravvivono a demote/reactivate e si intersecano a runtime con le aziende VIVE. **Budget AI-check** (`family_members.ai_check_budget`): NULL = illimitato, N ≥ 0 = tetto per ciclo; lo scalo è dal pool del titolare al CONSUMO, mai all'assegnazione (overbooking permesso per scelta).

- **`fn_create_family_member` NUOVA FIRMA a 7 argomenti** (`p_company_id`, `p_ai_check_budget`): la vecchia a 5 è DROPPATA (un CREATE OR REPLACE creerebbe un overload-bypass + ambiguità PGRST203; precedente repo 0003). Scrive membership + riga access. Errori nuovi: `company_required`, `company_not_found`.
- **`fn_set_member_company` / `fn_set_member_access` / `fn_set_member_budget`** — modifiche del membro sotto lock del padre, con audit; l'access-set deve includere l'appartenenza (`membership_access_required`); cambiare appartenenza NON revoca la visibilità della vecchia azienda.
- **`fn_reactivate_family_member`** — ripara l'appartenenza al rientro: se l'azienda non è più viva riassegna alla più vecchia viva dell'owner (+riga access); senza aziende resta NULL.
- **`fn_soft_delete_company`** — guard `company_has_members`: un'azienda con membership pending/active/demoted non si cancella finché il titolare non riassegna. L'ARCHIVIAZIONE (reconcile) invece NON è bloccata: il resolver fa fallback sulla più vecchia visibile.
- **`fn_create_company`** — deroga a N7 sulla PRIMA azienda viva: viene assegnata (appartenenza+visibilità) ai membri con appartenenza NULL; dalla seconda in poi la nuova azienda è invisibile ai membri finché non concessa.
- **`fn_backfill_famiglia_0031()`** — richiamabile (pattern 0028): appartenenza = azienda viva più vecchia dell'owner (il default storico del resolver), visibilità = TUTTE le vive correnti (zero regressioni di accesso al cutover), budget = 0 SOLO sulle righe NULL (i membri esistenti non possono lanciare AI-check finché il titolare non assegna: comportamento di oggi preservato). DO di verifica a WARNING.
- **Enforcement runtime**: il resolver `deps.active_company` per un membro ATTIVO risolve SOLO dentro visibilità ∩ vive (header fuori → 404; default = appartenenza → più vecchia visibile → nessuna); le **consulenze** (lista+dettaglio) e il **digest alert** (sezioni per azienda) sono filtrati sullo stesso insieme — erano i due percorsi fuori resolver.

- **`fn_partner_call_ai_prenota(owner, company, call, richiedente, servizio, budget, riserva, limite_call, limite_owner) → uuid`** — prenotazione atomica di un job AI (`partner_call_posizioni | partner_call_testi`, solo bozza, richiedente = titolare): job dello stesso servizio in corso da meno di 10 minuti → `ai_in_corso` (più vecchio: la sua esecuzione si chiude come interrotta); esecuzioni di oggi dello stesso servizio per **azienda × bando** (annullare e ricreare la bozza non azzera il conteggio) ≥ `limite_call` → `ai_limite_call`; esecuzioni di oggi dell'owner su **tutti** i servizi delle call insieme ≥ `limite_owner` → `ai_limite_owner` (NULL = nessun limite; stessa esclusione della 0034 per le esecuzioni chiuse senza chiamare il modello); poi `fn_partenariati_ai_prenota` (origine `call`, gruppo `altri`) per il budget (`ai_budget_esaurito`); il job diventa `in_corso` con la nuova esecuzione.
- **`fn_partner_call_ai_concludi(call, esecuzione, servizio, job_stato, proposta, errore_job, stato, costo, token_in, token_out, modello, errore) → {job_scritto, esecuzione_chiusa}`** — chiusura **atomica**: il job diventa `pronta` o `errore` solo se è ancora `in_corso` con quella esecuzione, e nella stessa transazione l'esecuzione si chiude solo se ancora `in_corso`. Il job registra il consumo solo con `esecuzione_chiusa = true`.
- **`fn_partner_call_ai_esecuzione_interrotta(esecuzione) → boolean`** e **`fn_partner_call_ai_chiudi_stale(minuti) → integer`** — failsafe (in lettura e nello scheduler, soglia `PARTNER_CALL_AI_STALE_MINUTI`, minimo 1): job in corso oltre la soglia → `errore` (`interrotta`, proposta svuotata) ed esecuzione chiusa a costo ignoto con una riga `timeout_unknown` nel registro consumi; lo stesso per le esecuzioni dei due servizi rimaste in corso senza un job che le referenzi. Salta le righe bloccate.
- **`fn_partenariati_snapshot(owner) → {call_attive: {limite, usate, residuo}, candidature_mese: {limite, usate, residuo, periodo_inizio, periodo_fine}}`** — per `/me/entitlements`: limite NULL = illimitato (residuo NULL), `usate` = call pubblicate o sospese delle aziende vive dell'owner, residuo mai negativo; mese solare Europe/Rome. Invarianti: una sola call non chiusa per azienda × bando; limiti di piano applicati solo sotto il lock dell'owner, sul pool di tutte le sue aziende vive; nessuna scrittura fuori dalle RPC (le tabelle sono chiuse ai client); una riga di consumo per esecuzione AI, scritta da chi la chiude (job o failsafe); le versioni pubblicate non cambiano; l'hard delete dell'azienda cancella call, requisiti, posizioni e versioni, le segnalazioni restano.

Y viva, visibile, non sospesa, che accetta inviti, di un altro owner e che non abbia già **rifiutato** un invito su questa call (il rifiuto vale per tutta la call), altrimenti `partner_non_disponibile` (codice neutro unico); call di X (`call_not_found`) aperta (`call_non_attiva`); posizione della call; inviti della call scaduti per TTL chiusi; un solo attivo per Y; inviti in attesa della call < `max_inviti` (`inviti_esauriti_call`). `scade_at = now() + ttl_giorni`; audit `partenariato.invito_inviato`. Anche un'azienda sul piano Gratuito riceve inviti.
- **`fn_partner_decidi(candidatura, attore, owner, company, decisione, motivo, rivela, richiedi_non_sandbox default true) → {candidatura, conversazione_id}`** — decide X le candidature e Y gli inviti (chiunque altro `candidatura_non_trovata`); stato `inviata` (`candidatura_gia_decisa`), invito non scaduto (`invito_scaduto`). **Rifiuto**: motivo facoltativo ≤ 500, audit `partenariato.candidatura_rifiutata`. **Accettazione** (K2), in una transazione: call aperta (`call_non_attiva`), identità di chi decide (`identita_non_verificata`), profilo partner di Y visibile e non sospeso (`profilo_partner_non_attivo` se decide Y, altrimenti `controparte_non_disponibile`), controparte viva — non eliminata né archiviata, con il profilo dell'owner attivo, come per il backend — e con identità verificata (`controparte_non_disponibile`), owner diversi (`stesso_gruppo`), esclusività (`esclusivita_violata`, dopo il lock advisory azienda × bando); poi conversazione, stato `accettata`, audit `partenariato.candidatura_accettata` e, **solo con `p_rivela`**, `partenariato.identita_rivelata` e `partenariato.contatti_rivelati` (oggi il backend passa sempre false).
- **`fn_partner_ritira(candidatura, attore, owner, company) → {candidatura}`** — Y ritira la propria candidatura, X il proprio invito (altrimenti `candidatura_non_trovata`), solo da `inviata` (`candidatura_gia_decisa`; invito scaduto → `invito_scaduto`). Audit `partenariato.candidatura_ritirata`.
- **`fn_partner_scadi_inviti(limite default 500) → integer`** — inviti in attesa oltre la scadenza → `scaduta` (`ttl`), i più vecchi per primi, al più `limite` (1..5000), saltando le righe bloccate (una decisione in corso vince). Scheduler e lettura pigra.
- **`fn_partner_scadi_per_opt_out(company) → integer`** — vedi il trigger sulla revoca.
- **`fn_partner_invia_messaggio(conversazione, attore, owner, company, testo, client_msg_id) → {messaggio, company_destinataria_id, duplicato}`** — solo il titolare di una delle due aziende (lock owner `FOR KEY SHARE` → azienda `FOR KEY SHARE` → conversazione `FOR UPDATE`); la stessa `client_msg_id` della stessa azienda restituisce il messaggio già scritto (`duplicato: true`, anche a conversazione chiusa); altrimenti conversazione aperta (`conversazione_chiusa`) e controparte viva: non eliminata né archiviata, owner attivo (`controparte_non_disponibile`); aggiorna l'ultimo messaggio e la lettura del mittente.
- **`fn_partner_segna_letto(conversazione, user, company, fino_a) → bigint`** — l'azienda è parte della conversazione e l'utente ne è titolare o membro attivo con visibilità (altrimenti `conversazione_non_trovata`, anche per un utente estraneo); solo in avanti e mai oltre l'ultimo messaggio (`fino_a` NULL = fino all'ultimo).
- **`fn_partner_claim_email_chat(conversazione, company, user_ids, ultimo_id) → setof uuid`** — claim a UPDATE condizionato per l'azienda destinataria: degli utenti indicati tiene solo titolare e membri attivi con visibilità (gli altri si ignorano) e rivendica chi non ha letto fino all'ultimo messaggio dell'altra azienda e non ha già un avviso in sospeso: **un avviso per raffica**, finché l'utente non legge.
- **`fn_partner_conversazioni_riepilogo(user, company)`** — le conversazioni dell'azienda con i non letti dell'utente (messaggi dell'altra azienda oltre la sua lettura, esclusi gli oscurati) e l'ultimo messaggio, in un solo round trip; nessuna riga per un utente estraneo.
- **`fn_partner_chiudi_conversazione(conversazione, attore, owner, company)`** — solo il titolare del creatore X (chiunque altro `conversazione_non_trovata`); `aperta → chiusa` (`conversazione_chiusa` se lo è già) + audit `partenariato.conversazione_chiusa`. Lo storico resta in sola lettura (K4).
- Ridefinite con la **stessa firma**: **`fn_partner_call_sostituisci_posizioni`** (la 0037 cancellava e reinseriva tutte le posizioni, azzerando `posizione_id` delle candidature: ora le posizioni conservate si aggiornano per id, si cancellano solo le omesse, e una posizione omessa con candidature attive → `posizione_con_candidature`); **`fn_partenariati_snapshot`** (candidature usate con `fn_partner_candidature_usate`); **`fn_partner_call_pubblica`** (in più l'esclusività alla pubblicazione, C6: l'azienda che pubblica non deve avere una candidatura accettata su un'altra call non annullata dello stesso bando se una delle due call è esclusiva → `esclusivita_violata`, con lo stesso lock advisory dell'accettazione).

**Esclusività** (`fn_partner_esclusivita_violata`, interna; la 0040 la estende ai membri del consorzio con la stessa firma, vedi sotto): l'azienda ha un altro impegno sullo stesso bando — è creatrice di un'altra call pubblicata oppure ha una candidatura accettata su un'altra call **non annullata** (completata, scaduta o sospesa contano ancora: il partenariato può essere andato avanti; l'accettata non si ritira) — e questa call o quella dell'altro impegno è esclusiva (il vincolo è del bando: basta che uno dei due creatori l'abbia confermato).

Invarianti: al più una candidatura o un invito attivo per call × azienda; transizioni solo dalle RPC; una conversazione per accettazione, creata con il suo audit nella stessa transazione; messaggi immutabili e idempotenti; al più un avviso email per raffica e per utente; chiusura della call e revoca dell'opt-in chiudono i pendenti anche quando arrivano da percorsi di sistema; nessuna scrittura dai client (tabelle chiuse, funzioni revocate). Cascade: dall'azienda (Y o X) candidature e conversazioni con messaggi e letture; dalla call le sue candidature e conversazioni; dall'utente le sue letture. Rollback documentato in coda al file (prima si riporta indietro il backend o si spegne il flag; le tre funzioni della 0037 si ripristinano prima di eliminare quelle nuove; le segnalazioni dei messaggi vanno esportate prima).

### Consorzio della call e validatore (migration 0040)

Consorzio delle call di partenariato e dati del validatore deterministico (WP8, docs/partenariati.md §2.8 V1-V3, Q11, Q20). Migration **additiva** (due tabelle, tre colonne di `partner_calls`, funzioni nuove; cinque funzioni della 0039 ridefinite con la **stessa firma**: una sola funzione per nome), da eseguire **in un'unica transazione** dopo la 0039. RLS deny-all + revoke sulle tabelle nuove, funzioni SECURITY DEFINER con `search_path` fissato ed EXECUTE revocato a `public`, `anon` e `authenticated` (interne e backfill comprese). Ogni transizione passa da una RPC. **Ordine dei lock** (quello globale): owner (`profiles FOR UPDATE`) → azienda che agisce → call (`FOR UPDATE` per il creatore, `FOR SHARE` per un membro) → membro (`FOR UPDATE`) → lock advisory per ultimo. Le RPC dei membri leggono prima la riga senza lock (per sapere su quale call agiscono) e poi bloccano in quest'ordine; `fn_partner_decidi` scrive le righe dei membri dopo il lock advisory dell'esclusività, che nessuna funzione dei membri prende.

- **`partner_call_membri`** — il consorzio della call (V1): `partner_call_id` (cascade), `company_profile_id` (azienda in piattaforma, cascade; NULL = membro **esterno**, Q20), `candidatura_id` (candidatura accettata da cui nasce la riga, unica, `on delete set null`), per gli esterni `esterno_denominazione` (2..200), `esterno_paese` (ISO2 maiuscolo) ed `esterno_tipi_soggetto text[]` (≤ 5 codici del vocabolario, validati dal backend) — obbligatori per gli esterni e assenti per le aziende (`pcm_esterno_coerente`; un esterno non ha candidatura) —, `posizione_id` (→ posizioni, `on delete set null`), `ruolo` (`capofila | partner | affiliated_entity | associated_partner`, default `partner`), `quota_percentuale numeric(5,2)` in (0, 100], `stato` (`proposto ⇄ confermato → uscito → proposto`), `confermato_da_user_id` e `aggiornato_da_user_id` (senza FK, mai verso terzi), `confermato_at`, `created_at`, `updated_at` con trigger. CHECK: `confermato` ⇔ `confermato_at` e `confermato_da_user_id`; confermato solo con la quota, salvo il **partner associato** (non riceve budget). Indici: una riga per azienda nella call (`partner_membri_azienda_uq`, anche uscita: si riammette), **capofila unico** tra i non usciti (`partner_membri_capofila_uq`), per call e stato, per azienda e stato (esclusività, cascade), per posizione.

- **`partner_calls`** — tre colonne tecniche, fuori dalla whitelist delle RPC della call: `validazione_esito` (`verde | rosso | grigio`, esito complessivo del validatore nella vista del creatore), `validazione_at` (insieme all'esito), `copertura_gap_ratio numeric(4,3)` (0..1: requisiti cercati coperti dal consorzio / cercati). RPC (revocate ai client, chiamate solo dal backend; il detail è il codice d'errore). Il consorzio si modifica solo con la call `pubblicata`, `scaduta` o `chiusa_completata` (altrimenti `call_non_modificabile`): alla scadenza della ricerca di partner il partenariato può andare avanti:
- **`fn_partner_membro_aggiorna(membro, attore, owner, company, posizione, ruolo, quota) → {membro, stato_precedente, modificato}`** — solo il creatore (titolare dell'azienda creatrice; per chiunque altro `membro_non_trovato`), su qualunque riga non uscita (`membro_uscito`), la propria compresa (per sé solo `capofila | partner`, `ruolo_non_ammesso`); posizione della call (`posizione_non_valida`), capofila unico (`capofila_gia_presente`, anche per concorrenza). - **`fn_partner_membro_conferma(membro, attore, owner, company, ruolo, posizione, quota) → {membro, stato_precedente, modificato}`** — l'azienda del membro conferma la propria riga (creatore compreso), il creatore anche quelle degli esterni (chiunque altro `membro_non_trovato`); azienda viva (`azienda_non_disponibile`), membro non uscito (`membro_uscito`); **ruolo, posizione e quota passati sono quelli che chi conferma ha visto** e devono coincidere con la riga bloccata (`membro_modificato`: una pagina non aggiornata, o una modifica concorrente del creatore, non fa confermare termini mai mostrati); quota presente salvo per il partner associato (`quota_mancante`). - **`fn_partner_membro_esci(membro, attore, owner, company) → {membro, stato_precedente, modificato, origine}`** — il creatore toglie un membro (stati modificabili) oppure un'azienda esce da sé, **in qualunque stato della call** e anche con l'azienda non più viva (`origine`: `creatore | membro`); la riga del creatore non si tocca (`membro_non_rimovibile`). - **`fn_partner_membro_esterno(call, attore, owner, company, payload jsonb) → {membro, creato, stato_precedente, modificato}`** — il creatore aggiunge o modifica un esterno: chiavi `{membro_id?, denominazione, paese, tipi_soggetto?, ruolo?, quota?, posizione_id?}` (altre → `parametri_non_validi`; tipi distinti, ≤ 5); tetto di **30 membri non usciti** e 60 righe esterne per call (`limite_membri`; un esterno uscito si ripropone modificandolo); posizione della call; capofila unico. - Ridefinite con la **stessa firma**: **`fn_partner_call_aperta`** (creatore vivo = non eliminato né archiviato **e** titolare attivo, come la controparte delle RPC del WP7 e l'indice del matching); **`fn_partner_esclusivita_violata`** (vedi sotto); **`fn_partner_decidi`** (all'accettazione, nella stessa transazione, la riga del creatore se manca e quella di Y: proposta, con la posizione della candidatura e la sua quota ipotizzata, capofila se la posizione lo è e il posto è libero; la risposta ha in più `membro_id`); **`fn_partner_call_pubblica`** (alla pubblicazione la riga del creatore); **`fn_partner_call_sostituisci_posizioni`** (in più: una posizione omessa a cui punta un membro non uscito → `posizione_con_membri`, così la posizione confermata di un membro non cambia senza una nuova conferma).

**Esclusività** (dalla 0040): l'azienda ha un altro impegno sullo stesso bando se è creatrice di un'altra call pubblicata, **o di un'altra call non annullata che ha ancora almeno un altro membro non uscito** (in piattaforma o esterno: il partenariato è partito; una call scaduta senza partner non blocca il suo creatore); se è **membro non uscito** (non creatore) di un'altra call non annullata; se ha una candidatura accettata su un'altra call non annullata **senza riga nel consorzio** (dati precedenti al backfill). ### Sicurezza

- **RLS deny-all**: RLS abilitata su tutte le tabelle (incluse `family_members`, `company_profiles`, `audit_log`) senza alcuna policy → `anon` e `authenticated` non leggono/scrivono nulla; il backend usa `service_role` che bypassa la RLS. In più, `REVOKE ALL` esplicito sui ruoli client.
- **RPC bloccate**: Supabase concede di default `EXECUTE` ad `anon`/`authenticated` su ogni funzione di `public`, e PostgREST le espone come `POST /rest/v1/rpc/<nome>`. Le migration revocano esplicitamente `EXECUTE` su `fn_switch_plan`, `promote_to_admin`, `fn_promote_progettista`, `fn_ensure_progettista_codice`, `fn_email_verificate`, sulle RPC multi-azienda (`fn_effective_max_aziende`, `fn_create_company`, `fn_soft_delete_company`, `fn_reconcile_companies`), sulle RPC delle consulenze (`fn_accept_proposal`, `fn_book_slot`, `fn_update_slot`, `fn_delete_slot`, `fn_create_slot_serie`, `fn_delete_slot_serie`) sulle RPC del modulo pagamenti (`fn_apply_plan_change`, `fn_complete_purchase`, `fn_fail_purchase`, `fn_execute_scheduled_change`, `fn_registra_cambio_admin`, `fn_next_invoice_number` — quest'ultima dormiente, senza chiamanti dal backend) e sulle RPC dell'inventario add-on (`fn_addon_apply_movement`, `fn_create_consultation_request`, `fn_admin_grant_addon`, `fn_admin_revoke_addon`, `fn_backfill_addon_ledger_0028`) e del motore entitlement (`fn_entitlement_extra`, `fn_entitlement_detail`, `fn_entitlement_limit`, `fn_entitlement_snapshot`, `fn_reconcile_family`, `fn_canonizza_addon_0030`) e dei bilanci (`fn_bilanci_registra_fonte`, `fn_bilanci_ricalcola_anno`, `fn_acquire_import_lock_token`, `fn_release_import_lock_token`, `fn_openapi_prenota_operazione`) e del bilancio ufficiale (`fn_bilancio_richiesta_crea`, `fn_bilancio_richiesta_chiudi`, `fn_bilancio_richiesta_claim_poll`, `fn_seed_addon_bilancio_ufficiale_0033`) dai ruoli client: senza queste revoche chiunque potrebbe auto-promuoversi, creare aziende altrui, assegnarsi consulenze o applicarsi piani a pagamento gratis.
- **Audit degli accessi full**: ogni lettura dei dati completi di un'azienda da parte del progettista assegnato scrive `consulenza.dossier_accessed` in `audit_log` (dal WP9 anche `consulenza.call_accessed` per la call di un consulto chiesto dalla call, scritto prima dei dati: senza audit niente dati; così i contesti dei messaggi segnalati letti dall'admin, `moderazione.contesto_accessed` / `moderazione.contesto_completo`) (oltre alle transizioni: `consulenza.created` / `proposal_sent` / `assigned` / `booked` / `cancelled` / `booking_cancelled`).

Catalogo dei bandi, alimentato esternamente. **BandoFit non vi scrive mai**: il backend usa la chiave `anon`, che per costruzione (RLS del secondario) consente solo SELECT. Il dump di riferimento è in `database_secondario_dump/` (solo locale, escluso da git).

Con il criterio di pubblicazione attuale questo avviene oggi per gli slug cambiati: doppioni fusi e bandi ritirati restano leggibili fino al passaggio alla vista pubblica (fase c), da cui la stessa risoluzione vale anche per loro.
